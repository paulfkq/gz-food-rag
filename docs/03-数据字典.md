## 3. 三个易混淆字段的精确语义（硬约束正确性关键）

| 字段 | 语义 | 用户说法 → 过滤逻辑 |
|---|---|---|
| `allergens` | 本店**含有**的过敏原（安全红线） | "花生过敏" → 排除 `allergens` 含"花生"的店 |
| `avoid_ingredients` | 本店**明确不使用或可去除**的食材（偏好） | "不要香菜" → **只召回** `avoid_ingredients` 含"香菜"的店 |
| `dietary_flags` | 饮食规范（宗教/文化） | "清真" → 只召回 `dietary_flags` 含"清真"的店 |

**为什么 `avoid_ingredients` 非空率只有 46.7%**：这是刻意的保守策略——未标注的店视为"无法保证不加香菜"，宁可少召回，也不能在忌口问题上误导用户。面试可讲。

**`allergens: []` 的边界**：表示"招牌菜未检出这 7 类过敏原"，**不等于全店绝对无过敏原**。真实生产必须接商户确认的过敏原表，这里是合成数据的已知局限，不要拿它对外做安全承诺。

## 5. 数据是怎么保证不"乱配"的

不是随机拼字段，而是 **12 个店铺原型 × 22 个真实商圈**：

1. **原型绑定**：每个原型固定菜系、价位区间、菜品池、过敏原、环境、场景、营业时段（如"潮汕牛肉火锅"必带沙茶酱→花生过敏原；"面家"必带麸质）。
2. **商圈绑定**：原型只允许出现在适配商圈（海鲜酒家不出现在西华路小吃街；肠粉店不出现在珠江新城核心写字楼）。
3. **商圈系数**：珠江新城 ×1.25、体育西 ×1.2；西华路/上下九 ×0.9，避免"老城区天价肠粉"。
4. **过敏原派生**：从实际选中的菜品过敏原取并集，而不是随机撒。
5. **固定 seed**：`--seed 20261116`，同样命令永远生成同样数据，评估可复现。

## 6. 内置校验规则（18 类，本批 0 错误）

- 字段集合完全等于 45 个 Schema 字段（不多不少）
- `district` 枚举合法；`noise_level` 仅安静/适中/吵
- `price_band` 与 `price_per_person` 一致
- `rating` 3.5–5.0；辣/甜/油 0–5
- `geo` 落在广州经纬度范围
- `allergens` 只允许 7 类合法值
- 8 个布尔字段类型正确；`synthetic` 恒 true
- `is_late_night` ↔ 营业时段含 00:00 之后
- `is_dim_sum` ↔ 营业开始 ≤07:00
- "老字号" ↔ `since_year` ≤1995
- "全素" ↔ 不含海鲜类过敏原
- `shop_id` / `name` 全局唯一

> 当前是零第三方依赖的校验器。Phase 0 建 venv 后会补上 Pydantic v2 的 `Shop` 模型，把这份规则迁成类型声明 + `model_validator`，校验能力不降级。

## 7. 已知边界（确认时请重点看这几条）

| 边界 | 说明 | 影响 |
|---|---|---|
| 坐标为商圈中心近似值 | 不是商户真实位置，±0.0025° 约 ±250m | 只用于 `geo_radius` 演示，不能当真实导航终点 |
| 步行分钟为合成值 | 地铁步行时长是虚构的 | 真实耗时属于架构红线 2 的富化层，不进本数据 |
| 评论文字虚构 | pros/cons 是模板化短句，不是真实点评 | 用于验证 pros/cons 分块，不能对外当口碑事实 |
| 过敏原仅基于招牌菜 | 见 §3 | 不作食品安全承诺 |
| 黄埔南岗海鲜酒家相对偏多 | 该区商圈数量少，原型适配集中 | 扩到 300 家后该区降到 40 家，偏差已缓解但仍存在 |
| 无实时排队数据 | 按红线 2 不进索引 | queue_min 是静态估计，不是实时值 |
