# Parent-Child 父子块切分：从原理到代码

> 对应代码：`scripts/chunker.py`（切分）、`scripts/build_index.py`（入库）
> 数据链路：`shops.jsonl`（300 家 × 45 字段）→ `chunks.jsonl`（2388 块）→ Qdrant（2088 个 Child）

---

## 1. 为什么不能按 512 token 无脑滑窗

餐厅是**实体型数据**：`店名 / 人均 / 过敏原 / 营业时间`这些字段强关联，缺一个就可能答错。固定窗口切分有两个致命问题：

1. **切开实体**：「人均 18 元」和「穗香居」被切到两个 chunk，问"西华路人均 20 以下的肠粉店"时，价格过滤和店名对不上。
2. **语义稀释**：好评「环境安静」和差评「夜间很吵」若在同一段文本里做 embedding，向量语义互相抵消，查"安静"反而可能召回这家吵的店。

结论：**按语义角色切，而不是按 token 数切**。这就是 Parent-Child 的本质。

---

## 2. 两层结构：谁存、谁检索、谁给 LLM

| 层 | chunk_type | 数量 | 进 Qdrant？ | 作用 |
|---|---|---:|---|---|
| **Parent 主档** | `parent` | 300（1/店） | ❌ 不进 | 全字段半结构化文本；命中 Child 后按 `parent_id` 回溯，作为 LLM 上下文 |
| **Child 概览** | `child_overview` | 300 | ✅ | 承接"XX 店怎么样"这类整体问法 |
| **Child 菜品** | `child_dish` | 888 | ✅ | 菜品级检索："哪家艇仔粥最正宗" |
| **Child 场景** | `child_scene` | 300 | ✅ | 抽象氛围："有烟火气""适合带爸妈" |
| **Child 好评** | `child_pros` | 300 | ✅ | 正面评价独立，避免被差评稀释 |
| **Child 争议** | `child_cons` | 300 | ✅ | 负面独立成块，承接"有没有踩雷" |

这是经典的 **small-to-big** 形态：用小块（Child）做精确检索，用大块（Parent）给足上下文。

**为什么不把 Parent 也向量化入库**（本项目的选择）：
- 优点：省一半编码时间与存储；检索目标纯粹，不会出现"Parent 和 Child 同时命中同一家店、占掉两个召回位"。
- 代价：无法直接对"整店描述"做语义召回。若需要，把 Parent 同样编码进库、用 `chunk_type` 区分即可——`build_index.py` 只需去掉 `if chunk_type != "parent"` 的过滤。

## 3. 每个 chunk 长什么样

切分产物 `chunks.jsonl` 每行结构：

```json
{
  "chunk_id": "GZ-HZ-0001::child_dish::1",
  "chunk_type": "child_dish",
  "source_shop_id": "GZ-HZ-0001",
  "parent_id": "GZ-HZ-0001::parent",
  "text": "西关号·江南西早茶（海珠区江南西，人均 ¥78）的招牌菜「流沙包」...",
  "payload": { "...硬约束字段冗余..." },
  "model_version": "bge-m3@2026-11"
}
```

- `chunk_id`：全局唯一，由 `店铺ID::角色::序号` 拼成；入库时哈希成 uint64 作为 Qdrant point id。
- `parent_id`：Child 指回 Parent；Parent 自己为 `null`。**回溯就靠这根指针**。
- `text`：真正被 BGE-M3 编码的文本。
- `payload`：检索时随向量一起存，供 pre-filter 用。

## 4. 核心实现细节（对应 chunker.py 的函数）

### 4.1 `render_parent()`：字段标题 + 值的半结构化文本

```
【店铺】西关号·江南西早茶（别名：...）｜ID GZ-HZ-0001
【位置】海珠区 / 江南西｜...｜地铁 2号线江南西站步行11分钟｜有停车位
【菜系】粤菜、广式点心｜招牌：流沙包、艇仔粥、叉烧包
【口味】清淡、鲜甜；辣度 0/5...
【价格】人均 ¥78（区间 61-100）
...
```

比纯 JSON 更适合 embedding（有自然语言连接），又比自由文本更利于保持字段边界。

### 4.2 `render_child()`：按角色生成单一意图文本

5 类 Child 各有模板，其中 pros 与 cons 严格分开——这是"安静 vs 吵"不互相污染的保证。

### 4.3 `_payload()`：硬约束字段冗余（最关键的一步）

每个 Child 的 payload 都复制一份父级硬约束字段：

```
district, business_area, cuisine, price_per_person, allergens,
avoid_ingredients, dietary_flags, geo, opening_hours, noise_level,
private_room, parking, is_late_night, is_dim_sum, metro_lines, metro_walk_min, ...
```

**为什么必须冗余**：硬约束靠 Qdrant 的 `pre-filter` 在向量检索**之前**就把不符合的店过滤掉。如果 Child 不带这些字段，过滤只能在 Parent 层做，命中 Child 后还要二次 join 店铺表——既慢又容易漏。冗余是"硬约束 100% 满足"的前提。

冗余带来的代价是存储膨胀（每个 Child 都存一份），但 2088 个块的体积极小，完全可接受。这是典型的空间换正确性。

### 4.4 派生过滤字段

`metro_lines`（地铁线路数组）、`metro_walk_min`（最短步行分钟）是从 `nearest_metro` 派生的，专门服务于"地铁 X 号线沿线""步行 10 分钟内"这类过滤。

## 5. 入库实现（对应 build_index.py）

1. **读 chunks.jsonl**，过滤出 `chunk_type != "parent"` 的 Child。
2. **BGE-M3 编码**：`BGEM3FlagModel(本地路径, use_fp16=False).encode(texts, return_dense=True, return_sparse=True)`。
   - 本机 FlagEmbedding 1.4.2 返回键是 `dense_vecs`（numpy 数组）和 `lexical_weights`（list of dict），不是旧版的 `dense` / `sparse`;
   - dense 做 L2 归一化后用 COSINE 距离——归一化是硬要求，否则 cosine ≠ 内积。
3. **Qdrant collection**：named vectors `dense`(1024) + `sparse`；建 payload/geo 索引。
4. **分批 upsert**：point id = `sha256(chunk_id)` 前 8 字节转 uint64，稳定可复现；重跑不会产生重复点。
5. **版本标注**：payload 带 `model_version`，将来换模型可原子切换 collection 做对照。

> 注意：Qdrant **embedded** 模式下 payload index 不生效（会打印 warning），过滤走精确扫描，结果正确。上生产换 Docker 版 Qdrant 即自动享受索引加速。

## 7. 面试怎么讲

- **为什么 Parent-Child**：实体型数据字段强关联，固定切分切开实体、稀释语义；按语义角色切 + 小块检索大块上下文。
- **为什么 pros/cons 分开**：负面评价混进正面向量会语义抵消，导致"安静"召回吵店。
- **为什么 payload 冗余**：硬约束要靠 pre-filter 在检索前过滤，Child 不带字段就无法在 Child 层过滤。
- **为什么 dense 要归一化**：cosine 距离只有归一化后才等价于内积，分数才可比。
- **embedded Qdrant 的坑**：payload index 不生效但结果正确，生产换 server 版。
