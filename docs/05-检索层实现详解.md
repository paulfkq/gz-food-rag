# 检索层实现详解｜从新手到能讲清每一环

> 对应代码：`scripts/retrieve/`（slots / filter_dsl / recall / fusion / verify / pipeline）+ `scripts/ask.py`
> 面向：第一次做 RAG 的人。每一环都按「是什么 → 为什么 → 怎么实现 → 坑」讲。
> 验证数据：300 家店 / 2388 chunk / Qdrant 2088 个 Child 向量；本机无 GPU，全程 CPU。

---

## 0. 先建立整体心智模型（别急着看代码）

把检索层想成一个**餐厅筛选流水线**。用户说一句"西华路人均30以下的肠粉，别太吵"，人脑会做这些事：

1. 听懂条件：位置=西华路、价格≤30、要肠粉、最好安静（"别太吵"是偏好不是硬性要求）
2. 先按硬性条件缩小范围：把不符合位置、价格的店直接排除
3. 在剩下的店里凭感觉找"像肠粉店"的（这是语义检索）
4. 也查一下"肠粉"这个词精确出现在哪些店（这是关键词检索）
5. 把两批结果合起来排个序
6. 逐个仔细核对："这家真的符合所有条件吗？"
7. 确认后，把这家店的完整档案拿出来给人看

这 7 步，就是检索层的 6 个环节（第 1 步=槽位解析，第 2 步=Filter，第 3~4 步=三路召回+融合，第 5 步=Rerank，第 6~7 步=复核+回溯）。

**一句话记住整套设计**：难的、规则的、不能错的事（硬约束）交给确定性代码；模糊的、语义的、可以错的事（排序、口味）交给模型。两者严格分层。

## 1. 为什么"槽位解析"是第一步，而不是直接丢给向量检索

### 是什么
槽位（slot）= 从自然语言里抽出来的结构化字段。比如：

```
"不要香菜和花生，人均80以内的粤菜"
  ↓ 槽位解析
{
  price_max: 80,                    # 硬约束
  cuisines: ["粤菜"],                # 硬约束
  exclude_allergens: ["花生"],       # 硬约束（店含花生 → 排除）
  require_avoid: ["香菜"],          # 硬约束（要求店明确标注不含香菜）
  soft: []                          # 软偏好
}
```

### 为什么必须有（这是新手最容易跳过、也最致命的一步）
如果直接把这句话编码成向量去检索，会发生三件坏事：

- **数值失效**：向量空间里 "30" 和 "500" 的距离很小，"人均30以内" 和 "人均500" 的向量可能很接近 → 推荐了根本去不起的店。
- **否定词失效**：embedding 是把整句话压成一个向量，"不要香菜" 里的 "香菜" 反而会把含香菜的店拉近 → 语义检索天生不擅长"不要"。
- **无法精确过滤**：没有结构化字段，就没法告诉数据库 `WHERE price <= 30 AND '花生' NOT IN allergens`。

所以必须先把话拆成**机器能执行的条件**。这一步的质量，决定了后面硬约束能不能 100% 满足。

### 怎么实现（`slots.py`）
两类解析器，产出同一个 `SearchSlots` 对象：

| 解析器 | 原理 | 优点 | 缺点 | 定位 |
|---|---|---|---|---|
| `RuleSlotParser`（默认） | 词典 + 正则 | 零依赖、可穷举、可单测、100% 确定 | 覆盖不了复杂口语 | **主用**，关键路径 |
| `llm_parse`（可选） | function calling | 能理解长尾口语 | 要 key、要网络、可能幻觉 | 补充，输出必须校验 |

关键设计点：

1. **硬约束和软偏好分开存**。`hard` 里的字段进过滤器，`soft` 里的只影响排序。"别太吵" → `soft: ["安静"]`，**不**设 `noise_level` 硬约束；但"必须安静" → `noise_level="安静"` 进硬约束。语气强弱决定落点，这是产品细节。
2. **否定词必须转成黑名单**。`_parse_negatives()` 用正则抓 "不要/别/忌/过敏/不吃" 后面的食材，再分流：
   - 过敏原词（花生、海鲜…）→ `exclude_allergens`：店**含有**就排除
   - 忌口食材（香菜、猪肉…）→ `require_avoid`：要求店**明确标注不使用**
   
   这两者语义完全不同，对应数据里 `allergens`（含有）和 `avoid_ingredients`（不使用）两个字段。搞混就是把"不要香菜"理解成"想要香菜"的元凶。
3. **不确定就留空，禁止猜测**。识别不出来就留给语义检索兜底。硬约束猜错 = 推荐了不该推荐的店，代价远大于漏一个条件。这是"宁可漏不可错"。
4. **冲突检测**。像"越秀区 + 人均30 + 米其林"这种自相矛盾的条件，检测出来置 `need_clarify=true` 直接追问，而不是硬凑一个答案。这是产品成熟度的体现。

### 自测结果（跑 `python -m retrieve.slots`）
```
Q: 不要香菜和花生，人均80以内的粤菜
   → 人均≤80 | 菜系=粤菜 | 排除过敏原=花生 | 要求不含=香菜
Q: 越秀区人均30米其林三星
   → need_clarify: 米其林(人均通常>¥100)与人均≤¥30冲突
```

### 坑
- **别用 LLM 直接生成过滤条件不做校验**。LLM 可能编造 `"price_max": -1` 或把否定词理解反。方案要求 LLM 输出过 Pydantic 风格校验后再执行；**受约束字段还要过枚举白名单**（`_normalize_llm_slots()`），LLM 把"肠粉"塞进 `cuisines` 会被降级为软偏好，否则 pre-filter 会把店全过滤光。
- **跨路径的确定性规则必须提到公共层**（实测踩坑）。冲突检测原先只写在 `RuleSlotParser.parse()` 里，默认改用 LLM 槽位解析后，"人均30米其林"在规则版正确追问、LLM 版却把"米其林"归进 soft 而静默放行——检索照常返回店、LLM 照常生成答案。现在抽成公共函数 `_detect_conflicts(s, text)`，规则版与 LLM 版都调用。**教训：凡是"检测到 X 就不检索"的硬规则，不能挂在单条分支上，新增分支时必须检查是否绕过了它。**
- **粤语口语要进同义词词典**。"抵食→性价比高""镬气→镬气足""唔好辣→不辣"，写在 `SYNONYMS` 里，加词不用改逻辑。

## 2. Filter 编译：硬约束的"前置闸门"

### 是什么
把 `SearchSlots` 翻译成 Qdrant 的 `Filter` 对象（类似 SQL 的 WHERE 子句），让向量检索**在候选阶段就排除**不符合的店。

### 为什么必须前置，而不是检索完再过滤
这是理解整个系统的关键。假设用户要"人均30以内"，库里大部分店人均 50+：

- **事后过滤**：向量检索先取 Top-50，其中可能只有 3 家 ≤30。真正符合的平价店因为向量分排第 60，根本没进 Top-50 → 召回被浪费。
- **前置过滤（pre-filter）**：先限定候选池 = {人均≤30 的店}，再在池子里按向量相似度排序 → 好店不会因为"总体排名靠后"被漏掉。

Qdrant 的 Filter 三个逻辑块：
- `must`：同时满足（AND）
- `should`：满足其一（OR）
- `must_not`：不能满足（NOT）——过敏原黑名单用它

### 怎么实现（`filter_dsl.py`）
`compile_filter()` 逐个字段翻译：

| 槽位字段 | Qdrant 写法 | 对应字段语义 |
|---|---|---|
| district / business_area | `MatchValue` | 精确匹配 |
| price_min / price_max | `Range(gte, lte)` | 数值区间 |
| cuisines | `MatchAny` | OR 匹配菜系 |
| **exclude_allergens** | `must_not + MatchAny` | 店**含有**过敏原 → 排除 |
| **require_avoid** | `must + MatchAny` | 要求店**标注不含**此食材 |
| metro_lines / max_walk_min | `MatchAny` / `Range` | 交通 |

编译出的 filter 会传给 dense 和 sparse 两路检索（`query_filter=qfilter`）。

### 能做 pre-filter 的前提：入库时 payload 冗余
这一点在上一环节（父子块）就埋好了伏笔：每个 Child 的 payload 都复制了父级的硬约束字段（`district`、`price`、`allergens`、`geo`…）。**如果 Child 没冗余这些字段，pre-filter 就只能作用在 Parent 层，命中 Child 后还要二次 join**——复杂且易漏。所以"空间换正确性"是入库时就定下的设计。

### 坑：BM25 路绕过了 pre-filter
这是我在实测中踩到并当场修复的坑。**BM25 是内存索引，不经过 Qdrant**，所以 dense/sparse 被 filter 挡掉了含花生的店，BM25 却把它们召回来了，混进融合后又被后置复核剔光 → 过敏 query 返回结果为空。

修复：BM25 召回后立刻用同一套 `verify_hard()` 过滤（见 pipeline.py 第 ③ 步）。这就是"双保险"的价值——任何一路漏网，后置复核都能兜住。

## 3. 三路召回：三种"看法"找候选

### 是什么、为什么三路都要
| 路 | 原理 | 擅长 | 弱点 |
|---|---|---|---|
| **dense** | query/doc 各编码成 1024 维向量，比 cosine | 语义："安静适合约会" 能召回写"灯光柔和"的店 | 数值、否定、专名不敏感 |
| **sparse** | BGE-M3 的词级权重（学出来的） | 关键词匹配，带一点语义扩展 | 模型词表外的词无效 |
| **BM25** | jieba 分词 + TF-IDF 统计 | 粤语专名、新词精确命中（"啫啫煲"） | 完全不懂语义 |

关键认知：**三路来自同一份文本，但错误模式不同**。dense 会在专名上失手，BM25 会在语义上失手，sparse 居中。三者融合才稳定——这是面试能讲出深度的地方。

为什么 sparse 和 BM25 不重复：sparse 是**模型词表**上的权重，遇到没登录的方言新词可能失效；jieba + 自定义词典是**确定性**的，能兜住长尾。二者互补。

### 怎么实现（`recall.py`）
- `Encoder.encode_query()`：BGE-M3 一次编码同时产出 dense（L2 归一化）和 sparse（`lexical_weights`）。**一次前向拿两种向量，几乎零额外成本**——这是选 BGE-M3"三合一"的核心收益。
- `dense_recall()` / `sparse_recall()`：调 Qdrant 的 `query_points`，带 `query_filter=qfilter`。
- `BM25Index`：启动时用 jieba 对 2388 个 Child 文本分词建倒排索引，pickle 缓存到 `data/bm25.pkl`，之后直接读缓存。加了自定义词典（啫啫煲、泮塘、马蹄糕…）避免切碎专名。

一个实现细节：dense/sparse 从 Qdrant 拿到的 payload 里**没有 chunk_id 和 text**（入库时只写了业务 payload），所以 BM25 路要手动把这两个字段塞回 payload，保证三路的 `Candidate` 结构一致，融合时能按 chunk_id 对齐。

### 坑
- **dense 必须 L2 归一化**，否则 cosine 距离 ≠ 内积，分数失真（入库时和查询时都要归一化）。
- **BM25 分数无上界**，不能和 cosine 直接比较——所以才需要 RRF（下一环）。

## 4. RRF 融合：只看排名，不看分数

### 是什么、为什么
三路的分数尺度完全不同：cosine 在 [0,1]、BM25 无上界、sparse 又是一套。**加权求和需要先归一化，而归一化对离群值极敏感，还要不停调权重 α**。

RRF（Reciprocal Rank Fusion, Cormack 2009）的天才之处：**完全无视分数，只看排名**：

```
RRF(d) = Σ  1 / (k + rank_i(d))      k = 60
```

一条店在三路都排第 1 → 分数最高；只在一路出现、还排第 30 → 分数很低。尺度无关、无需训练、10 行代码、鲁棒。

### 怎么实现（`fusion.py` 的 `rrf_fuse()`）
1. 每路内部按自己的 score 降序，确定 rank（1-based）
2. 同一 `chunk_id` 在多路出现时，累加 RRF 分数、合并来源 `sources`
3. 按总分降序输出

`sources` 会记进 trace——你能看到"这家店被 dense+bm25 同时命中"还是"只有 bm25 命中"，这是排查召回问题的依据。

### 坑
- 进阶可讲 `weighted RRF`（给不同路不同权重）、LTR（有标注后训练排序器）、以及把"硬约束命中数"当 tie-breaker。但起步阶段基础 RRF 就够，别一上来堆复杂度。

## 5. Rerank 精排：cross-encoder 修正"语义相近但条件不符"

### 是什么、为什么必须有
RRF 后的 Top-50 交给 BGE-Reranker-v2-M3 逐个 `(query, doc)` 打分，取 Top-8。

为什么 dense 不够，还要 rerank？这是 bi-encoder 的死穴：

> dense 把 query 和 doc **各自**编码后比较，二者"从未见过面"，所以分不清"人均500"和"人均80以内"的关系——token 相似就给高分。
> cross-encoder 把 `(query, doc)` **拼在一起**过一遍注意力，能做细粒度交互，才发现"500 > 80，这家不该排前面"。

用方案里的反例：查"天河区 人均500 的精致粤菜"，纯向量会把"天河/粤菜/清淡"高度重合的平价店排很前；cross-encoder 能判断数值冲突。

### 代价与取舍
cross-encoder 是 `O(n)` 次前向（每条候选一次），CPU 上慢。所以**只对 Top-50 精排**，不是全库。实测本机 50 条约几秒。若延迟不可接受，降级路径是 FlashRank(ONNX) 或云 Rerank API——"有降级路径"本身就是可落地性的体现。

### 怎么实现（`fusion.py` 的 `Reranker`）
`FlagReranker(use_fp16=False, normalize=True)` + `compute_score(pairs)`，分数归一化到 0~1 便于解释。

### 坑：一个实测观察到的现象
花生过敏 query 的精排分普遍偏低（0.1~0.2），因为 Reranker 对"过敏原排除"这种**否定语义**天生不擅长。但这**不影响正确性**——过敏约束由前面的 Filter 和后面的复核保证，Rerank 只负责排序。"硬约束不交给模型软判断"这条铁律在这里再次得到验证：正好因为没让 Rerank 管过敏，才没出事。

## 6. 硬约束后置复核 + Parent 回溯（small-to-big）

### 两件事，两个理由

**① 后置复核（双保险第二道）**
Rerank 后的 Top-8 逐家再验一次硬约束。pre-filter 已经挡过一道，为什么还要挡？

- BM25 路在内存跑，不过 Qdrant filter（已在第 2 环修复，但安全带保留）
- RRF / Rerank 是代码逻辑，可能有 bug 让不合条件的候选混进来
- 过敏约束错一次就是事故，**宁可现在多一次 O(n) 的 Python 判断（n≤50）**

`verify_hard()` 和 `compile_filter()` 检查的是同一批字段，一个在数据库层、一个在内存层，构成双保险。

**② Parent 回溯（small-to-big）**
检索用 Child（粒度细、语义纯、命中准），但送给 LLM 的应该是 Parent（全字段主档）。如果直接把命中的"菜品块"丢给 LLM，它可能只看到"流沙包好吃"，看不到"人均78、含花生"——答案就会缺信息甚至张冠李戴。

所以：命中 Child → 记下 `parent_id` → 从 Parent store 取回完整主档。这就是 "small-to-big"（小块检索、大块使用）。

### 怎么实现（`verify.py`）
- `ParentStore`：启动时从 chunks.jsonl 读出所有 parent，按 `parent_id` 建索引
- `verify_and_expand()`：复核 → 回溯 → **按 shop_id 去重**（一家店可能多个 Child 都命中，只保留分数最高的，其余 child_id 记下来供引用）→ 输出 `FinalHit`

`FinalHit` 里带 `matched_hard`（命中哪些硬约束）和 `matched_soft`（命中哪些软偏好），供生成层解释"为什么推荐这家"。

### 坑
- 不去重会让同一家店在结果里出现好几次（概览块、菜品块各一次），浪费 LLM 上下文还让答案啰嗦。
- Parent 回溯失败要记录并剔除，不能静默跳过——否则答案引用对不上主档。

## 7. 总控与可观测性（`pipeline.py`）

`RetrievalPipeline` 把六步串起来，两个工程要点：

1. **重资源只加载一次**：Encoder / Reranker / BM25 / ParentStore 在 `__init__` 里加载（约 20s），之后每条 query 复用。否则每条都加载 2.2GB 权重完全不能用。
2. **完整 trace**：每步的中间结果（槽位、filter、三路各自 Top-K、RRF 前后、rerank 分数、被剔除的候选、各步耗时）都记下来。没有这套日志，出问题只能靠猜。加 `--trace` 可打印。

冲突时 early return：`need_clarify=true` 时直接返回追问，不硬凑答案。

## 9. 面试高频追问（检索层专项）

1. **为什么不直接把 query 丢给向量检索，要先做槽位解析？** → 数值/否定词在 embedding 里失效，无法编译成精确过滤；硬约束错一次是事故。
2. **pre-filter 和 post-filter 有什么区别？各自什么时候用？** → pre 在候选阶段缩小池子防召回浪费；post 兜底防漏网。本项目两个都用（Qdrant filter + verify_hard）。
3. **BM25 路为什么特殊处理？** → 它在内存里跑，不过 Qdrant filter，必须手动补一道硬过滤，否则污染融合。
4. **三路召回为什么不是两路？sparse 和 BM25 重复吗？** → 错误模式不同；sparse 是模型词表权重，BM25 是确定性统计，对新词/方言互补。
5. **RRF 为什么只看排名不看分数？** → 三路分数尺度不可比，加权要归一化且对离群敏感；RRF 尺度无关、免调参。
6. **为什么需要 cross-encoder rerank？bi-encoder 的死穴是什么？** → bi-encoder 分开编码无法交互，分不清数值/否定；cross-encoder 拼接后过注意力能细粒度判断。
7. **rerank 对否定语义（过敏）不擅长怎么办？** → 不让 rerank 管硬约束；过敏交给 filter + 后置复核，rerank 只管排序。分层是关键。
8. **什么是 small-to-big？为什么检索用 Child 送 LLM 用 Parent？** → 小块语义纯命中准，大块信息全；命中小块回溯大块，避免答案只见树木不见森林。
9. **为什么重资源要启动时加载一次？** → 每条 query 加载 2.2GB 权重不可用；初始化成本摊薄到所有请求。
10. **怎么证明你的硬约束是 100% 满足的？** → trace 记录被剔除的候选及原因；golden set 上单列"约束满足率"指标，必须 100%。
