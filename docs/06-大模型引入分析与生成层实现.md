# 06 大模型引入分析与生成层实现

> 回答三个问题：① 槽位解析是不是提取检索关键词？② 借助大模型是不是更好？③ RAG 三阶段（入库 / 检索 / 回答）哪个该引入大模型？
> 所有结论都带**本地实测数据**（接口：`http://127.0.0.1:8600/v1`，模型 `glm-5.3-flash`）。
> 对应代码：`scripts/retrieve/slots.py`（LLM 槽位解析）、`scripts/generate/`（生成层）、`scripts/answer.py`（端到端入口）。

---

## 1. 先纠正一个概念：槽位解析不是"提关键词"

你说"槽位解析是不是从用户输入中提取用于检索的关键词信息"——方向对，但不精确。它提取的不是**关键词**，而是**结构化的检索条件（slot）**，而且分两类：

| 类型 | 例子 | 去向 | 错了的后果 |
|---|---|---|---|
| **硬约束 hard** | 人均≤30、越秀区、排除花生、要包间 | 编译成 Qdrant 精确 filter，在向量检索**前**生效 | **事故**：把含花生的店推给过敏用户 |
| **软偏好 soft** | 安静、性价比高、有镬气、适合带爸妈 | 进入语义召回、影响排序 | 体验差一点，可接受 |

关键词只是软偏好里的一小部分（`肠粉`、`啫啫煲`这类专名）。真正值钱的是把"人均30以内"翻译成 `price_max=30`、把"花生过敏"翻译成 `exclude_allergens=["花生"]`——这是**字段 + 值 + 语义角色**，不是一串关键词。

这一步是整条链路的"翻译官"：后面的过滤器、召回、融合都只认这个结构化对象，不再去猜用户原话。

## 2. 三阶段该不该用大模型：哑铃结构

判断标准只有一条：

> **语义理解 / 语言生成 → 用 LLM；精确过滤 / 稳定排序 → 用代码和专用模型。**

由此得出一个"两端重、中间轻"的**哑铃结构**：

| 阶段 | 具体环节 | 用 LLM？ | 用什么 | 根因 |
|---|---|---|---|---|
| **向量化入库** | 解析 / 切块 / embedding | ❌ 主流程不用 | PyMuPDF / chunker / BGE-M3 | embedding 是专用模型的活，用 LLM 生成向量又慢又贵还不一定适合检索；离线链路要可复现 |
| | 文档字段抽取 / 摘要 / doc2query | ⭕ 可选增强 | LLM（离线跑） | 非结构化文档才需要；本项目数据是结构化 JSON，字段齐全，用不上 |
| **检索** | **槽位解析** | ✅ **该用** | LLM function calling + 规则兜底 | 本质是自然语言理解，LLM 强项；长尾口语规则覆盖不全 |
| | 三路召回 / RRF 融合 | ❌ 不用 | BGE-M3 / BM25 / 代码 | 精确召回与融合是确定性算法，LLM 又慢又不稳定 |
| | Rerank | ❌ 不用 | bge-reranker（cross-encoder） | 专用精排模型比 LLM-as-reranker 更快、更准、更省 |
| | 硬约束复核 / Parent 回溯 | ❌ 坚决不用 | 代码 | 安全红线，必须 100% 确定，绝不交给模型软判断 |
| **回答生成** | 组织自然语言答案 | ✅ **最该用** | LLM + 引用校验 | 本质是"基于证据的语言生成"，LLM 的核心价值所在；模板答案只能列字段 |

**一句话记忆法**：LLM 用在**入口（听懂用户）**和**出口（说清答案）**，中间的检索管线全是确定性工程。

## 3. 槽位解析：上 LLM 到底好在哪？（实测）

### 3.1 测试方法与结果

用 6 条 query 对比规则版（`RuleSlotParser`）和 LLM 版（`llm_parse`，function calling，本地 glm-5.3-flash）：

| Query | 规则版 | LLM 版 | 判断 |
|---|---|---|---|
| "珠江新城附近找个不适合谈事、能带狗的平价小店" | 商圈=珠江新城 | 商圈=珠江新城 + 软偏好=**宠物友好/热闹/平价** | LLM 明显更优："不适合谈事"→热闹、"能带狗"→宠物友好，规则词典完全没有这些词 |
| "想带爸妈吃点清淡的，不要那种很油的，环境要能聊天" | 软偏好=带爸妈 | 软偏好=**清淡/少油/安静** | LLM 明显更优：规则只认出"带爸妈"，"清淡/少油/能聊天"全漏 |
| "一个人安安静静吃、不用排长队的粉面店" | 软偏好=安静/一人食 | 软偏好=**适合一个人/安静/不用排长队/粉面** | LLM 更全：多认出"不用排长队" |
| "不吃带壳海鲜、户外位、别太贵、七八十一人" | 菜系=海鲜 + 排除海鲜 + 户外 + **误判一人食** | 人均≤80 + 排除甲壳类 + 软偏好=户外 | 各有问题：规则误把"七八十一人"的"一人"当一人食；LLM 的过敏原值不在受约束词表（见 3.3） |
| "人均30以内的肠粉" | 人均≤30 | 人均≤30 + 软偏好=肠粉 | 打平，简单 query 规则版足够 |
| "不要香菜和花生" | 排除花生 + 要求不含香菜 | 排除花生 + 要求不含香菜 | 打平，硬约束两边都对 |

### 3.2 结论：语义理解上 LLM 确实更好，但有两个前提

**好在哪**：口语、隐含、长尾表达——"不适合谈事""能带狗""清淡少油""不用排队"——规则词典永远列不全，LLM 的语义泛化能力是降维打击。**如果你的用户会自然说话，LLM 槽位解析值得上。**

**但必须守住两条边界**（这是能不能上线的分水岭）：

1. **LLM 只输出 slots，绝不执行过滤**。过滤必须由确定性代码做（`filter_dsl.py`）。让 LLM 直接决定"这家店符不符合"= 把安全红线交给概率模型 = 事故。
2. **必须有规则兜底 + 输出校验**。LLM 超时、返回非法 JSON、字段值不在受约束词表——任一情况都要能降级到规则版（`parse_slots` 里已实现）。简单 query 用规则版 0ms、零成本，没必要每次都调 LLM。

### 3.3 实测发现的新坑：LLM 输出的"值"不受控

这是这次实测最有价值的发现。LLM 理解对了吗？对了（"带壳海鲜"它理解成甲壳类）。但它输出的值是 `exclude_allergens=["甲壳类海鲜", "蟹", "虾", "虾壳"]`——而数据里的标准词是 `["虾/甲壳类"]`。**直接把这个值塞进 Qdrant filter，一个店都匹不到。**

这就是"NLU 强 ≠ 可用"的典型：LLM 懂语义，但不懂你数据库里的枚举值。解决办法有三层（本项目按需取用）：

- **prompt 里给候选枚举**：把 `CUISINES / DISTRICTS / ALLERGEN_CANON` 列进 system prompt，让模型从封闭集合里选。
- **输出后做 canonical 归一化**：像规则版 `ALLERGEN_CANON` 那样，把"蟹/虾壳"映射到"虾/甲壳类"（推荐，最稳）。
- **schema 校验**：Pydantic 风格，值不在枚举内 → 该字段丢弃，降级语义召回。

> 面试讲点："LLM 做槽位的难点不在理解，在于把开放的自然语言输出**对齐到封闭的数据库枚举**。这是 NLU 到可执行的 filter 之间最后一道坎。"

### 3.4 延迟事实（诚实记录）

本地 glm-5.3-flash 是 **reasoning 模型**，单次 function calling 约 **5.7~9 秒**（规则版 0~2ms）。这是"语义理解更强"的代价：

- 本地 CPU / reasoning 模型：延迟高，适合**离线预解析**或对延迟不敏感的场景。
- 生产要低延迟：换非 reasoning 的快模型 / 云端 API，或**只在规则版解析失败时才调 LLM**（懒调用）。
- 本项目默认仍是规则版，`prefer_llm=True` 且配好 key 才走 LLM——这个取舍是对的。

## 4. 回答生成：为什么要"再丢给模型组织一次"（实测）

### 4.1 模板答案 vs LLM 答案

**模板版**（`AnswerGenerator._template`，零 key 兜底）长这样：

```
1. 桥头轩·西华路肠粉[1] —— 人均 ¥16｜评分 4.4｜荔湾区 / 西华路｜含过敏原：海鲜、花生
2. 合兴庭·西华路肠粉[2] —— 人均 ¥23｜评分 4.4｜荔湾区 / 西华路｜含过敏原：海鲜、花生
```

**LLM 版**（实测输出，引用校验 pass）：

> 为你找到 2 家西华路人均 30 以下的肠粉店。
> **1. 桥头轩·西华路肠粉[2]** —— 人均最低，¥16，性价比 4.4，评分 4.4（3777 条）……地铁 1号线陈家祠站步行 5 分钟，有停车位。注意：下午常售罄，排队约 17 分钟。
> **2. 合兴庭·西华路肠粉[1]** —— 人均 ¥23……同样皮薄透亮、平靓正……
> 两家都是 06:00-14:00 营业……对海鲜、虾/甲壳类、花生、麸质过敏的话要注意……（引用省略）

**LLM 多做了三件模板做不到的事**：
1. **结合用户条件解释推荐**——"人均最低""同样皮薄透亮"是对比出来的，模板只会平铺。
2. **归纳共性**——"两家都 06:00-14:00 营业""都不适合夜宵"，把重复信息收拢。
3. **主动提醒**——过敏提醒用户没问但很重要（从证据里的过敏原字段推导），体验差距明显。

**结论：值得。** 生成层是 LLM 在 RAG 里最不可替代的价值点。检索再准，最后给用户看的是答案——答案能不能"听懂问题、说人话、给理由"，全靠这一步。

### 4.2 但 LLM 会编造和搞错引用（实测抓到的真问题）

第二次实测（"花生过敏，人均50以内的粤菜"），LLM 输出了这样的句子：

> 榕荫轩·岗顶大排档[**2 的编号对应错了，这里是 [1]**] —— 人均 ¥50……

两个问题同时出现：
1. **推理泄漏**：reasoning 模型的思考过程漏进了正文（"编号对应错了"）。
2. **引用错位**：把榕荫轩标成 [2]，实际召回集里它是 [1]——店和编号对不上，用户按图索骥会找错店。

这证明：**prompt 里写"必须准确引用"只是劝，不能全信**。必须有代码校验。

### 4.3 生成层的三道防线（已实现）

```
LLM 生成答案
   → ① 引用校验 guard.py：编号合法？店名/编号对齐？无推理泄漏？价格数字来自资料？
   → 校验通过 → 用 LLM 答案（体验好）
   → 校验失败 → ② 降级到模板答案（零幻觉，编号由代码生成，100% 正确）
   → LLM 不可用/超时 → ③ 直接模板答案
```

`guard.py` 的四条规则都是这次实测**从真实错误里长出来的**：

| 规则 | 拦什么 | 单测结果 |
|---|---|---|
| 引用编号合法性 | `[9]` 但只召回 2 家 | BLOCK ✓ |
| 店名/编号对齐 | `榕荫轩[1]` 但 [1] 是明记轩 | BLOCK ✓ |
| 推理泄漏 | 答案含"编号对应错了" | BLOCK ✓ |
| 价格数字溯源 | 答案写 ¥999 但资料没有 | BLOCK ✓ |
| 简称容错 | "明记轩"（全称"明记轩·林和西面家"） | PASS ✓（不误伤） |

复测结果：同样的 query，LLM 再次把编号搞错，`guard` 准确拦下并自动降级——最终输出的是编号 100% 正确的模板答案。**"答案可降级，系统不能挂"，这就是工程化的价值。**

## 5. 落地配置（你的本地接口）

### 5.1 环境变量

> ⚠️ **Windows PowerShell 不要用 `export`**（那是 Linux/macOS 语法，在 PowerShell 里不生效）——
> 这正是"输出显示 LLM 0ms / 模板降级"最常见的原因。按你的终端选对应写法：

**Windows PowerShell（本机环境，用这个）：**
```powershell
$env:RAG_LLM_API_KEY="sk-wb-local-8600"
$env:RAG_LLM_BASE_URL="http://127.0.0.1:8600/v1"
$env:RAG_LLM_MODEL="glm-5.3-flash"
```

**Linux / macOS（或 Git Bash）：**
```bash
export RAG_LLM_API_KEY="sk-wb-local-8600"
export RAG_LLM_BASE_URL="http://127.0.0.1:8600/v1"
export RAG_LLM_MODEL="glm-5.3-flash"
```

> 说明：环境变量只在**当前终端会话**有效，关掉窗口就没了，下次要重设。
> 想永久生效可在 PowerShell 执行
> `[Environment]::SetEnvironmentVariable('RAG_LLM_API_KEY','sk-wb-local-8600','User')` 等（重开终端生效）。
> 没配 key 时系统不会报错，而是**静默降级到规则解析 + 模板答案**（优雅降级），
> 判断依据：看输出行的 `生成模式` 是 `llm` 还是 `template`、`LLM xxxms` 是否为 0。

### 5.2 跑起来

```bash
cd gz-food-rag/scripts
python answer.py "西华路人均30以下的肠粉"          # 检索 + LLM 生成 + 引用校验
python answer.py "不要香菜和花生" --no-llm          # 强制模板版（零 key 也能跑）
python ask.py "西华路人均30以下的肠粉" --trace      # 只看检索层 trace
```

### 5.3 接入时踩的兼容坑（已修，值得记）

| 坑 | 现象 | 解决 |
|---|---|---|
| 强制 tool_choice 不被接受 | SDK 传 `{"type":"function","function":{"name":...}}` → 400 `request_invalid_parameter`；curl 传 `"auto"` 正常 | 改用 `tool_choice="auto"` + 代码校验 `tool_calls`（网关普遍只支持 auto） |
| reasoning 模型 content 为空 | 纯 chat 时思考耗尽 `max_tokens`，`content=null`、答案在 `reasoning_content` | `max_tokens` 给足；只读 content，空则视为失败降级 |
| 依赖缺失 | venv 无 `openai` | 已装 `openai 3.51.0` |
