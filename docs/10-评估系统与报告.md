# 广州美食 RAG · 评估报告

> 生成时间：2026-11-17 11:32　|　Gold Set：40 条　|　运行配置：full, dense_only, no_rerank, no_hard_filter, rule_slots
> 纯 CPU 环境（BGE-M3 + BGE-Reranker-v2-M3 + 本地 glm-5.3-flash）

## 1. 评估方法

### 1.1 Gold Set 构建

- 从 300 家种子数据程序化生成问答对（固定 seed=42，可复现 `python eval/goldset.py`）。
- ground truth 由**结构化字段确定性过滤**得出（不用被测 pipeline 自己造答案），每家店的 parent 主档作为 RAGAS 的 gold contexts。
- 覆盖价格+商圈、区域+菜系、过敏原、场景、夜宵/早茶、地铁等 7 类查询，另含冲突追问样本（如「人均30米其林」）。

### 1.2 指标分层（为什么不是全用 RAGAS）

| 层次 | 指标 | 类型 | 作用 |
|---|---|---|---|
| 检索 | Recall@K / Precision@K / MRR / Hit Rate / nDCG | 确定性 | ID 集合精确计算，快、可复现，消融主力 |
| 约束 | 硬约束遵守率 | 确定性 | 安全红线（过敏/价格/商圈）是否守住 |
| 入口 | 槽位字段准确率 | 确定性 | 定位「检索差」是入口解析的锅还是召回的锅 |
| 生成 | 店铺名覆盖率 | 确定性 | 答案是否提到了 gold 店铺 |
| 语义 | Faithfulness / Answer Relevancy / Context Precision / Context Recall | RAGAS | 语义质量，按论文定义自实现，本地 LLM 做 judge |

- RAGAS 每条需 4~5 次 LLM judge 调用，只对 full 配置、前若干样本跑；消融实验用确定性指标，避免把算力烧在 judge 上。
- judge 结果按「样本+指标」缓存到 `eval/out/judge_cache.jsonl`，重跑不重复计费。

| 配置 | Recall@K | Precision@K | MRR | 硬约束遵守 | 平均延迟 | ΔRecall vs full |

## 4. 关键发现（由本次数据自动推导）

1. **约束守住但召回不足**：完整系统硬约束遵守率 1.000、Recall@K 仅 0.489。两者背离说明瓶颈不在过滤（错店没混进来），而在「最终 Top-N 店铺的覆盖」——rerank 的 topn 是 **chunk 级**，同一家店的概览/菜品/口味块会占掉多个名额，8 个 chunk 可能只覆盖 2~3 家店。若要提升店铺级 Recall，应改为按 shop_id 去重后取 Top-N，而不是简单调大 chunk topn（那会拖慢 rerank 且仍可能重复）。
2. **两类指标互相印证**：RAGAS Context Recall=0.491 与确定性 Recall@K=0.489 接近，说明 LLM judge 的归因判断与 ID 集合计算在这批数据上结论一致，指标不是各说各话。
3. **冲突检测有漏网**：追问命中率 0.50（2 条冲突样本）。「人均30米其林」这类明示词能触发，但「人均20块的高档海鲜私房菜」这类模糊高端表述未触发 —— 触发词表目前主要覆盖米其林/黑珍珠等明示词，「高档/私房/奢华」等隐含矛盾需要补进规则或交给 LLM 解析链路。
4. **答案忠实度较高**（Faithfulness=0.995）：LLM 答案里的陈述绝大多数能在检索上下文里找到依据，与 guard 引用校验 + 模板降级的设计一致 —— 生成层没有成为幻觉重灾区。
5. **去掉 Rerank**：去掉后 Recall@K 反而 **上升 +0.278** —— 该组件在当前 chunk 级 topn 设置下可能**伤害了店铺级覆盖**（同一家店的多个 chunk 被精排到前列、挤掉其他店的名额）。这是消融最有价值的产出：发现「看起来高级的组件其实在拖后腿」，若确认应改为先按 shop_id 去重再精排，而不是直接下掉该组件。
6. **去掉硬约束**：Recall@K 下降 -0.168，说明该组件对召回有正向贡献。
7. **硬约束双保险有效**：关掉 pre-filter + 后置复核后，遵守率从 1.000 掉到 0.622。说明两道检查确实在拦不合格店铺，而不是摆设。
8. **仅 Dense 单路**：Recall@K 下降 -0.140，说明该组件对召回有正向贡献。
9. **规则版槽位解析**：Recall@K 变化 +0.017（不显著），该组件的价值可能体现在其他维度（如精度/约束/忠实度），不能只看召回。

## 5. 偏差与限制

1. **合成数据**：店铺评分/价格/评论均为 synthetic（固定 seed），分布比真实数据规整；指标绝对值不能直接外推到线上，但组件间的相对差异有参考价值。
2. **样本量**：纯 CPU 单轮检索 ~15-20s、RAGAS judge 每样本 4~5 次 LLM 调用，默认只跑有限样本；小样本下方差较大，Δ 小于 0.02 视为不显著。
3. **LLM judge 偏差**：本地 glm judge 与生成用的是同一模型，存在「自评偏好」风险；Faithfulness/Relevancy 数值宜作趋势参考而非绝对真值。
4. **Recall 口径**：按 shop_id 去重计算；当前 rerank topn 是 chunk 级，店铺级覆盖会低于 chunk 级召回，这是系统设计取舍而非评估 bug。


## 7. 面试讲点

1. **评估要分层**：确定性指标做回归主指标，RAGAS 做语义补充 —— 前者快且可复现，后者有 judge 偏差但能测「忠实度/相关性」这类语义维度。
2. **消融要单变量**：每个配置只改一个组件，Δ 才能归因；全开/全关的对比说明不了任何事。
3. **Gold Set 不能自证**：ground truth 用原始结构化数据独立过滤，不用被测 pipeline 生成，避免「自己判自己」的循环论证。
4. **入口也要评估**：槽位字段准确率单列，能把「检索差」拆解成「解析错」还是「召回错」，定位问题的粒度直接决定优化方向。
5. **成本工程**：一次加载模型、逐条落盘断点续跑、RAGAS 缓存 —— 纯 CPU 环境下不做这些，评估根本跑不完。
